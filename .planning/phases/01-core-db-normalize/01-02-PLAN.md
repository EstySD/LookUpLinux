`_snapshot(conn, path, old_version) -> Path` (D-14): create `sqlite3.connect()` to a temporary file named `<db name>.bak-v<old_version>.<os.getpid()>.tmp` beside the database, copy with `conn.backup(dst)` (a consistent snapshot including WAL content; a plain file copy would miss WAL rows), close the destination and return the temporary path; remove the temporary file if anything fails. IMPORTANT: call it only while the connection has NO open transaction. Verified on 2026-10-24 (Python 3.14.3): `Connection.backup` called while the same connection holds a `BEGIN IMMEDIATE` write transaction on a WAL database hangs forever. `_snapshot` is called from exactly one place, step 6 below.

`open_store(path=None, migrations=MIGRATIONS, timeout=5.0) -> sqlite3.Connection`. LOCKED ORDER: keep the numbered steps in this sequence; the reason is given for each step because reordering any of them is the known way to break D-14.
1. `path = Path(path)` when given, else `default_db_path()`.
2. `conn = _connect(path, timeout)` (Task 1: SQLite version floor, parent directory with mode 0o700, autocommit connection, busy_timeout). From here every failure path closes `conn` before the exception leaves.
3. Read `PRAGMA user_version` into `v`; `target = len(migrations)`. If `v > target`, close and raise `SchemaTooNewError` whose message holds both integers and tells the user to update the program (Russian text, versions only). Why here: this happens before any write and before the WAL switch, so the refused file stays byte-identical (D-14).
4. `_ensure_wal(conn)`, then `PRAGMA synchronous=NORMAL` (D-19). Why after step 3: the WAL switch writes to the file.
5. If `v == target`, skip to step 9: no transaction is opened, so a normal hotkey call never takes the write lock for migration.
6. If `v > 0`, take `tmp = _snapshot(conn, path, v)`. Why here: the snapshot is taken BEFORE `BEGIN IMMEDIATE` and never inside it, because a backup from the connection that holds the write transaction hangs forever (see `_snapshot`). A fresh file (`v == 0`) is never backed up.
7. Run `BEGIN IMMEDIATE` and everything after it inside one try block, so a lock timeout on `BEGIN IMMEDIATE` is cleaned up like any other failure:
   a. re-read `user_version` as `locked_v` under the lock;
   b. if `locked_v > target`: ROLLBACK, close, delete the temporary snapshot if one exists, raise `SchemaTooNewError` unwrapped (not as `MigrationError`);
   c. stale-snapshot guard: if a snapshot exists and `locked_v == v`, publish it with `os.replace(tmp, <db name>.bak-v<v>)` in the same directory; if `locked_v != v`, delete the temporary file instead (another process migrated meanwhile, and its pre-migration backup must not be overwritten by a post-migration snapshot);
   d. apply `migrations[locked_v:]` in order, each as `step(conn)`;
   e. execute `PRAGMA user_version = %d` (spelled exactly so, spaces around `=`) with `target`;
   f. `COMMIT`.
8. Failure handling around step 7: on any `Exception` other than `SchemaTooNewError`, ROLLBACK when `conn.in_transaction`, close, remove a leftover temporary snapshot, and raise `MigrationError` chained from it (message: the original exception text); on any other `BaseException`, roll back when in a transaction, close, clean up, and re-raise unchanged. All steps and the version bump therefore commit together or not at all (D-14).
9. Return `conn` (default row factory).
